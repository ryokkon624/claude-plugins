# E. 自己判断の記録と検知

## この軸で見ること

AI が「良かれと思って」依頼されていない判断で対応したこと——置いた前提、指示や仕様からの逸脱、スコープの拡張、妥協——が**記録され**、その記録が**人間の目に届き**、記録漏れを**検知できる**か。

## check 一覧

| ID | チェック | severity 目安 | basis |
|---|---|---|---|
| E1 | 前提・逸脱・スコープ拡張・妥協を記録する指示がハーネスにある | should | custom |
| E2 | 記録先が人間の目に触れる経路にある（最終報告、PR 本文、レビュー対象の成果物、通知など） | should | custom |
| E3 | 「該当なし」も明示させている（記録ゼロと未記録を区別できる） | nice to have | custom |
| E4 | 人間の注意力に頼らない検知の仕組みがある（依頼範囲外の変更を検出する hook、レビュアーへの「スコープ外の変更を報告せよ」の指示、成果物の範囲チェックなど） | should | custom |
| E5 | ②で抽出した judgment_point（AI が裁量で判断する箇所）ごとに、記録の指示が付いている | should | custom |

## 公式

出典（取得日 2026-09-25）:
- https://code.claude.com/docs/en/best-practices — レビュー用 subagent のプロンプト例に「**nothing outside the task's scope changed**（タスクの範囲外が変更されていないこと）を確認し、ギャップを報告せよ」がある `[BP]`。「成功を主張するのではなく**証拠を見せろ**（テスト出力、実行したコマンドとその結果、スクリーンショット）」`[BP]`
- https://code.claude.com/docs/en/memory — auto memory の `feedback` 種別は「ユーザーの修正と、確認済みのやり方」を保存する `[HARD]`。これはユーザーが言ったことの記録であって、AI 自身の判断の記録ではない

公式が言っているのは「レビュアーにスコープ外の変更を報告させる」（E4 の一形態）と「証拠を見せろ」まで。**AI が自分の判断を記録する仕組み、記録先、検知については、公式の記述はない。** E1〜E5 は独自基準。

## 独自

### なぜ必要か

- エージェントは指示が曖昧なとき、聞くより「もっともらしく埋める」ほうに倒れる。埋めた前提は成果物に溶け込み、報告には出てこない
- 「依頼されていないが良かれと思ってやったこと」は、やった直後は親切に見え、あとで一番高くつく（仕様外の挙動、触るべきでないファイルの変更、テストの黙らせ）
- 記録があっても、誰も見ないファイルに書かれていれば意味がない。検知は人間の注意力に頼ると必ず漏れる

### 何をもって「ある」とするか

- **E1（記録の指示）**：「仕様にない判断・変更・妥協点が発生したら `<場所>` に追記する」のような、**トリガー（いつ）・対象（何を）・場所（どこに）**が揃った指示。「注意深く作業する」「必要なら報告する」は指示にならない
- **E2（経路）**：記録先が (a) 最終報告のテンプレートに組み込まれている、(b) PR 本文やレビュー成果物に含まれる、(c) レビュアーの入力になっている、のいずれか。memory ファイルに書くだけで、それを読む step がなければ不十分
- **E3（該当なし）**：「記録がゼロの場合は『特になし』と明記する」のような指示。これがないと、空欄が「なかった」のか「書き忘れた」のか区別できない
- **E4（検知）**：人間以外が検知する仕組み。例：Stop / PostToolUse hook で依頼範囲（Issue に紐づくファイル等）外の変更を検出する、レビュアー agent の指示に「スコープ外の変更・仕様にない挙動を列挙せよ」がある、成果物のチェックリストに「変更ファイル一覧が依頼範囲と一致するか」がある
- **E5（judgment_point ごと）**：②の `judgment_points[]` で `logging_instructed: false` のものが finding 候補。フロー単位で見る

### severity の考え方

- E1 がまったくない：should。エージェントが実装・執筆など成果物を作るフローが 1 つでもあれば該当する
- E1 はあるが E2 がない（書きっぱなし）：should
- E4 がない：should。ただし成果物が小さく人間が全量レビューする運用なら nice to have に下げてよい
- E3：nice to have

## 判定の手引き

### evidence の探し方

1. `harness.json` の `files[].hints.memory` と `memory[]` で、「判断」「逸脱」「前提」「妥協」「仕様外」「assumption」「deviation」「decided」を含む記録指示を探す（E1）
2. その記録先が `flows.json` のどこかで `inputs` になっているか、`artifacts` として報告・PR に含まれるか、レビュアーの参照になっているかを追う（E2）
3. `flows.json` の `judgment_points[]` を全部見る（E5）。`logging_instructed: false` を列挙する
4. `harness.json` の `hooks[]` に Stop / PostToolUse / SubagentStop があれば、スクリプトを Read して何を検出しているか見る（E4）。agent 定義（reviewer 系）の本文に「スコープ外」「仕様にない」の指示があるか見る（E4）
5. 最終報告や完了報告のテンプレート（skill 本文、templates/）に「自己判断」「前提」「特になし」の欄があるか見る（E2, E3）

### proposal の粒度

- E1 がない場合：どのフローのどの step に、次のような一文を足すかを書く

  > AC・仕様・指示に書かれていない判断・変更・妥協点が発生したら、そのたびに `<場所>` に「何を・なぜ・代替案」を追記する。ゼロの場合は完了報告に「自己判断: なし」と明記する

- E2 がない場合：既存の記録先を、最終報告テンプレートや PR 本文テンプレートのどこに差し込むかを書く。またはレビュアー agent の入力に加える
- E4 がない場合：
  - hook 案：`Stop` で `git diff --name-only` を取り、依頼範囲（例：Issue 番号に紐づくファイル、または事前に宣言したファイル一覧）と突き合わせ、範囲外があれば exit 2 で報告を求める。具体的な matcher と command まで書く
  - reviewer 案：reviewer agent の本文に「スコープ外の変更、仕様にない挙動、黙らせたテスト・lint を必ず列挙する」を足す
- E5：該当 judgment_point の step に、記録先と一文を足す

### よくある誤判定

- 「ユーザーに確認する」指示（AskUserQuestion 等）があれば、その判断点は**記録より前に人間が関与している**ので E5 の finding にしない。ただし「確認せず進めてよい」と書かれている判断点は対象
- memory への「学んだこと」の記録は E1 ではない（それは振り返りであって、成果物に埋め込まれた判断の開示ではない）
- 「実装ノート」「implementation-notes」のように名前が違っても、トリガー・対象・場所が揃っていれば E1 の pass。名前で判定しない
- E4 で hook がないことだけを理由に must にしない。検知は複数の形があり、reviewer への指示でも成立する
