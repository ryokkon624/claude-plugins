# C. レビュー行為

## この軸で見ること

フローの中で成果物を作る作業のそれぞれに、**その作業の性質に見合った検査・検証**があるか。goal が明確な作業には「回せるチェック」が、正解のない作業には「別コンテキストによる敵対的検証」が要る。あわせて、レビュアーの独立性、基準の明文化、不合格時の経路を見る。

## 作業の性質の判定

| 性質 | 判定基準 | 例 | 期待するレビュー |
|---|---|---|---|
| **goal 明確** | テスト・仕様・受け入れ条件・フォーマット規約など、合否を機械的または客観的に出せる基準が存在する、または作れる | 機能実装（AC あり）、バグ修正（再現テストあり）、リファクタ（既存テスト）、lint / 型、移行（前後の同値性） | 基準を回す検査。script / hook でもよいし、agent が実行してもよい |
| **正解なし** | 複数の妥当な答えがあり、良し悪しが基準ではなく判断で決まる | 設計・アーキテクチャの選択、計画・優先順位、仕様の詳細化、文章、**レビュー結果そのもの**、セキュリティ評価の妥当性 | 別コンテキストが**反証を試み、verdict を出す**敵対的検証 |
| **混在** | 機能実装は AC に対しては goal 明確だが、内部の設計判断は正解なし | 大きめの機能実装、API 設計を伴う実装 | 両方。AC の検査 ＋ 設計判断の検証 |

## check 一覧

| ID | チェック | severity 目安 | basis | 対象 |
|---|---|---|---|---|
| C1 | goal が明確な作業に、基準を回す検査の step がある（テスト実行、lint、spec / AC 照合、ビルド） | should | official | flow |
| C2 | 正解のない作業に、別コンテキストによる敵対的検証（反証を試み verdict を出す）の step がある | should | custom | flow |
| C3 | レビュアー / 検証者が作業者と別コンテキストである（同じセッション・同じ agent 内の自己レビューではない） | should | official | flow |
| C4 | 不合格時の経路が定義されている（誰に差し戻すか、回数上限、人間へのエスカレーション） | should | custom | flow |
| C5 | レビューの基準が明文化され、レビュアーに渡っている（spec / AC / 規約 / チェックリスト。「正確性と要件に関わるギャップだけを報告せよ」の類の絞り込み） | should | official | flow |
| C6 | レビュアー / 作業者が証拠を出すよう指示されている（テスト出力、該当行、実行コマンドと結果） | nice to have | official | flow |
| C7 | 決定的にできる検査が、散文の依頼ではなく hook / script で強制されている | nice to have | official | flow |

## 公式

出典（取得日 2026-09-25）: https://code.claude.com/docs/en/best-practices

- `[BP]` **「Claude が回せるチェックを与えろ**：テスト、ビルド、比較用のスクリーンショット。見張るセッションと、離れられるセッションの違いはそこにある」。「チェックがなければ『できたように見える』が唯一の信号になり、あなたが検証ループになる。合否を出すものを与えれば、ループは自分で閉じる」（C1）
- `[BP]` 停止をチェックで gate する 4 つの方法（設定コストの低い順）：(1) 同じプロンプト内で回す、(2) `/goal` で別の評価器に毎ターン再チェックさせる、(3) **Stop hook でスクリプトを走らせ、通るまでターンを終わらせない**（8 回連続ブロックで Claude Code が上書きして終了）、(4) **検証 subagent や dynamic workflow で「fresh なモデルに結果の反証を試みさせ、作業した agent が採点者にならないようにする」**（C1, C2, C3, C7）
- `[BP]` **「Add an adversarial review step」**：「タスクを完了扱いする前に、subagent に fresh context で diff をレビューさせ、ギャップを報告させろ」。「fresh な subagent コンテキストで動くレビュアーは、渡された diff と基準だけを見て、変更を生んだ推論は見ない。だから結果をそれ自身の条件で評価する」（C2, C3, C5）
- `[BP]` Writer / Reviewer のセッション分離：「fresh context はレビューを改善する。Claude は自分が書いたばかりのコードに偏らない」（C3）
- `[BP]` レビュアーへの絞り込み：「ギャップを探せと言われたレビュアーは、作業が健全でも何か報告する。すべてを追うと過剰設計になる。**正確性と明示された要件に関わるギャップだけを報告させ、残りは任意扱いにせよ**」（C5）
- `[BP]` 「成功を主張するのではなく**証拠を見せろ**：テスト出力、実行したコマンドと返り値、スクリーンショット。証拠を見るほうが再検証より速く、見ていなかったセッションでも効く」（C6）
- `[BP]` 「検証できないなら出荷するな（If you can't verify it, don't ship it）」— 失敗パターン "trust-then-verify gap" の処方（C1）
- `[BP]` `/code-review`（同梱 skill）は現在の diff を fresh な subagent でレビューする（C2 の実装例）

公式は「fresh context の subagent に反証させる」ところまで言っている。ただし対象は主に **diff（コード）** で、設計・計画・文章のような正解のない成果物にどう当てるかは書かれていない。C2 が custom なのはこのため。

## 独自

### なぜ「正解なし」に敵対的検証を要求するか

- 正解のない成果物（設計、計画、文章、レビュー結果）を通常のレビューにかけると、レビュアーは**同意するだけになる**。もっともらしい案には反対材料が見えにくく、「良さそう」で通る。これは経験則として何度も観測されている
- 品質を上げたいなら、レビュアーに「良いか」ではなく「**壊せるか**」を問う必要がある。反証を試みて失敗したことが、その案の強さの証拠になる
- 敵対的検証は verdict（成立 / 不成立 / 判断保留）を出させることで初めて機能する。「懸念点を列挙」だけだと、作業者が都合よく拾う

### 敵対的検証の最低要件

1. 別コンテキスト（fresh な subagent、または別セッション）
2. 入力は成果物と基準だけ。作業者の推論過程は渡さない
3. 指示は「反証せよ」：前提の誤り、見落とされた代替案、基準との矛盾、実現不能な仮定を探す
4. 出力は verdict ＋ 根拠。正確性・要件に関わるものだけを報告（公式の絞り込みをここでも適用）
5. 不成立のときの経路（C4）がある

### C4（不合格時の経路）を独自基準にする理由

公式は Stop hook の 8 回上限や `/goal` の停止のような**システム側の安全弁**は書いているが、ハーネス側で「レビュー不合格 → 誰に戻し、何回まで、それでもダメなら人間へ」を定義せよとは言っていない。定義がないと、不合格が無限ループするか、黙って通される。

## 判定の手引き

### evidence の探し方

1. `flows.json` の各フローで `artifacts[]` が空でない step を列挙する。これが「作業」
2. 各作業の性質を上の表で判定する。混在なら両方
3. `review_points[]` を見る。作業に対応する review_point があるか、`reviewer` が作業者と別の actor か（C3）、`criteria` が `none stated` でないか（C5）、`on_fail` が `none stated` でないか（C4）
4. review_point の `reviewer` が agent なら、その agent 定義（`harness.json` の `agent:<name>`）を Read し、「反証」「ギャップ」「スコープ外」「証拠」の指示があるか見る（C2, C5, C6）
5. `harness.json` の `hooks[]` に Stop / PostToolUse でテスト・lint を走らせるものがあるか見る（C7）。散文で「テストを実行すること」とだけ書かれている作業は C7 の候補

### proposal の粒度

- C1 がない：どの step の後に、何を実行し（コマンドまで）、結果をどこに出すかを書く。hook でできるなら hook の event / matcher / command まで
- C2 がない：検証 agent の定義（既存の reviewer 系 agent があればその流用）と、渡す入力、プロンプトの骨子を書く。例：

  > `agent:design-verifier`（tools: Read, Grep）に `<成果物>` と `<基準>` だけを渡し、「この設計を壊せるか試せ。前提の誤り、見落とした代替案、基準との矛盾を探し、CONFIRMED / REJECTED / PLAUSIBLE の verdict と根拠を返せ。正確性と要件に関わるものだけを報告せよ」

- C3 違反（自己レビュー）：レビュー step を別 agent に切り出す提案。既存の agent 一覧から候補を挙げる
- C4 がない：`on_fail` の一文を該当 step に足す。「不合格なら DEV に差し戻し、3 回で SM が人間に判断を仰ぐ」のように、差し戻し先・回数・エスカレーション先を埋める
- C5 がない：レビュアーに渡す基準の所在（spec / AC / 規約ファイル）を明示する一文と、絞り込みの一文
- C6 / C7：足す一文、または hook の定義

### よくある誤判定

- レビュアー agent が存在するだけでは pass にならない。**そのフローのその作業に対して起動される step があるか**を見る
- `convention-reviewer` のような規約レビューは C1（goal 明確：規約という基準がある）の検査であって、C2 の敵対的検証ではない。設計判断に対する C2 が別途あるかを見る
- 人間がレビューする運用（PR レビュー、承認待ち）は C3 を満たす。ただし「人間が見る」と書いてあるだけで、何を基準に見るかがなければ C5 の finding
- security-verifier のように「検証」と名乗る agent は、本文を読んで反証を試みる指示があるかで判定する。名前で判定しない
- ①②のレビューをするこのツール自身にも同じ基準が適用される（ADR-0005）
